# HW/SW Co-design Project — Benchmark Optimization, Analysis and Hardware Acceleration

ECE 00460882, Technion. Two pyperformance benchmarks profiled and optimized, plus a
pipelined hardware accelerator designed and verified in SystemVerilog for the kernel
they share.

## Results

| benchmark | before | after | speedup | correctness check |
|---|---|---|---|---|
| **nbody** | 107 ms | 96.7 ms | **1.11x** (9.9%) | total energy matches to 1.3e-15 (tolerance 1e-12) |
| **raytrace** | 367 ms | 229 ms | **1.60x** (37.6%) | rendered image, 30,000 bytes, **exact** match |

Both clear the assignment's 7% requirement. Every number above was measured inside the
course VM with a noise floor taken in the same session — see
[Trusting the numbers](#trusting-the-numbers).

**Hardware:** one pipelined datapath (sum three squares → inverse square root) with two
entry points, one per benchmark. All five testbenches pass. Predicted speedups are 2.66x
(nbody) and 2.04x (raytrace) by Amdahl's law. **The hardware was not synthesised and no
end-to-end speedup was measured** — those figures are bounded predictions, not results.

## Reproducing

### 0. Prerequisites

Everything below assumes the **course VM**: Ubuntu 22.04 under QEMU with KVM. The
timings are not reproducible on a different machine — see
[`results/ENVIRONMENT.md`](results/ENVIRONMENT.md) for why the glibc and Python
versions specifically change the outcome.

```bash
git clone <this repository>
cd <this repository>
bash scripts/setup_env.sh
```

`setup_env.sh` installs the toolchain, creates a virtualenv, sets the perf kernel
settings, and then **verifies that profiling actually works** by recording a real
one-second profile and failing if it collected too few samples. That last check is not
cosmetic — see [Trusting the numbers](#trusting-the-numbers).

### 1. The easy way

```bash
bash script_nbody.sh          # baseline, profile, optimize, compare
bash script_raytrace.sh
```

Each script is idempotent and runs the whole pipeline for one benchmark.

### 2. Step by step

**The two benchmarks use different settings, and you must not mix them.** Each one's
`PROCESSES`/`VALUES` is the setting whose noise floor passes — see
[Trusting the numbers](#trusting-the-numbers). Running raytrace at nbody's setting, or
either at pyperf's defaults, produces numbers that no floor in this repository
licenses.

```bash
# ---- nbody: 60 processes x 5 values ----------------------------------------
TAG=repro BENCHES=nbody PROCESSES=60 VALUES=5 bash scripts/run_baseline.sh
TAG=repro BENCHES=nbody UNWIND=fp DBG_LOOPS=20 bash scripts/run_profile.sh
TAG=repro BENCHES=nbody PROCESSES=60 VALUES=5 bash scripts/run_ablation.sh
TAG=repro BENCHES=nbody PROCESSES=60 VALUES=5 ROUNDS=3 bash scripts/run_final.sh

# ---- raytrace: 20 processes x 3 values -------------------------------------
TAG=repro BENCHES=raytrace PROCESSES=20 VALUES=3 bash scripts/run_baseline.sh
TAG=repro BENCHES=raytrace UNWIND=fp bash scripts/run_profile.sh
TAG=repro BENCHES=raytrace PROCESSES=20 VALUES=3 bash scripts/run_ablation.sh
TAG=repro BENCHES=raytrace PROCESSES=20 VALUES=3 ROUNDS=3 bash scripts/run_final.sh
```

`TAG` controls the suffix on every output file. **It defaults to `repro` above on
purpose:** with `TAG=kvm` a reproduction run would *overwrite* the committed evidence
files that the reports cite (`results/compare/nbody_final_kvm0921.txt`,
`raytrace_final_kvm.txt` and the rest). Tagged `repro`, the new results land beside the
originals so you can compare them rather than destroy them. Use `TAG=kvm` only if you
deliberately want to regenerate in place.

`script_nbody.sh` and `script_raytrace.sh` in section 1 do exactly the above with the
correct settings already applied, which is why they are the recommended route.

### 3. Correctness on its own

```bash
python3 scripts/make_variants.py      # regenerate all variants from the originals
python3 tests/check_equivalence.py    # check all 9 against the originals
```

Expected: `CORRECTNESS GATE PASSED for all 9 variants`.

### 4. The hardware

```bash
export PATH="$HOME/.local/bin:$PATH"     # if iverilog is installed there
python3 hw/golden/model.py               # the reference model's self-test
python3 hw/golden/model.py --vectors     # regenerate the test vectors
cd hw/sim && make all                    # build and run all 5 testbenches
```

Expected: `ALL TESTBENCHES PASSED`.

```bash
python3 hw/golden/call_overhead.py       # the Python→hardware boundary cost
python3 hw/golden/amdahl.py              # the speedup ceiling
python3 hw/golden/precision_study.py     # what 32-bit costs in accuracy
cd hw/sw && python3 setup.py build_ext --inplace   # build the driver
```

## Trusting the numbers

This is the part of the project we spent the most effort on, and the part most worth
reading if you only read one section.

### The noise floor

Before optimizing anything, we checked how accurately the machine can measure at all.
The test: run the **unchanged** benchmark, run it **again**, and compare the two runs.
The code is identical, so the true difference is zero — anything observed is
measurement error, and that bounds the smallest effect we could honestly claim.

```
results/compare/nbody_noise_floor_kvm0921.txt
results/compare/raytrace_noise_floor_kvm.txt

Benchmark hidden because not significant (1): nbody
Benchmark hidden because not significant (1): raytrace
```

**`not significant` is the goal, not a failure.** It means the two runs could not be
told apart — which is correct, because they are the same program.

It did not pass first time. nbody's floor came back at **1.10x** — a 10% difference
between a program and itself — at 20 processes × 3 values. Raising it to 60 × 5 (360
measurements per side) fixed it. That is why the commands above specify
`PROCESSES=60 VALUES=5`: **a noise floor only licenses claims measured the same way.**

### Three things we caught by being careful

1. **perf was secretly sampling at 1 Hz instead of 999 Hz.** No error was reported —
   it exited successfully and produced a valid-looking flame graph built on 8 samples.
   Two complete profile sets were discarded. `setup_env.sh` now records a real profile
   and *fails* if the sample count is too low.

2. **One profile was 69% Python startup**, not the benchmark. Read off that profile,
   the hottest line looks like 5.22%; off the clean one it is **18.11%**.

3. **We compared two different sessions and nearly published the conclusion.** A
   1-vCPU-versus-2-vCPU test appeared to show a 40% difference. Measured within the
   same session the two were indistinguishable; the gap was between *sessions*. It is
   recorded as inconclusive in `results/ENVIRONMENT.md` and no claim is drawn from it.

The rule those produced, which every check in this repository now follows:

> **An exit code proves a program ran. It does not prove it did its job.**

### A result we measured and refused to use

One nbody run came back at **1.20x**, better than the 1.11x reported. We did not use
it: the machine was ~45% slower that morning, the spread was 21% of the mean, and the
run had no same-session noise floor. It is kept as
`results/compare/nbody_final_noisy_20260921_kvm.txt` with a note saying not to cite it.

## The hardware in brief

```
fp32_mul + fp32_add          the only two arithmetic units in the design
     │
     ├──→ dot3      9 cycles     3 multiplies → 2-level adder tree
     └──→ rsqrt    25 cycles     64-entry table + 2 Newton steps
              │
              ├──→ pe_pair   49 cycles, II=1    the nbody kernel
              └──→ pe_ray    49 cycles, II=1    the raytrace kernel
                        │
                        └──→ accel_top   control registers, DMA, 10-state FSM
```

`dot3` and `rsqrt` are **shared** — both processing elements instantiate the same
modules. That is what makes "one accelerator, two benchmarks" structural rather than a
claim.

Subtraction is `fp32_add` with a sign bit flipped. The `-1.5` power has **no hardware at
all**: `r³` where `r = 1/√d2` *is* `d2^-1.5`, so two extra multiplies replace a whole
power unit.

**Verification:**

```
tb_dot3       512 vectors, 0 errors                          PASS
tb_rsqrt      512 vectors, max 0 ULP (budget 4)              PASS
tb_pe_pair    512 vectors, 0 errors                          PASS
tb_pe_ray     512 vectors (262 hits, 250 misses), 0 errors   PASS
tb_accel_top  80 pairs in 1629 cycles                        PASS
```

But "the tests pass" is not the real answer to *how do you know it works*. **Simulation
found seven specific bugs**, and that is the answer — including one that
`tb_dot3`'s 512 random vectors could never have found, because it only appears when a
vector is dotted with *itself*. Coverage is about the distribution of inputs, not the
count. See [`docs/hw/03_floating_point.md`](docs/hw/03_floating_point.md).

## What this project did not do

Stated plainly rather than left to be discovered:

- **The hardware was not synthesised.** 500 MHz is a target. There is no timing report,
  no area figure and no power figure.
- **No FPGA, no end-to-end measurement.** The benchmarks were never run with the
  accelerator attached. 2.66x and 2.04x are calculated predictions.
- **The AXI interfaces are simplified** — single-beat AXI4-Lite control and a sequential
  master, not protocol-complete AXI4.
- **nbody is too small for this hardware**, and our own simulation says so: 1629 cycles
  for 80 pairs is 20 cycles per pair, not the 1 the pipeline can achieve. 27%
  utilisation, because 5 bodies cannot fill a 49-stage pipeline.

The measured speedups in this project are the **software** ones. The hardware is a
design-and-analysis proposal, which is what the assignment asks for.
