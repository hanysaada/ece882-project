 E — HARDWARE  (assignment section 7)
################################################################################

[E1] Write the golden model in binary32 before any RTL, and use it to pick the
     rsqrt design point rather than choosing one.
     PROMPT AS SENT:
       "can u install iverilog/verilator? in this box?"
RESULT: 2ff5784. Swept accuracy surface: 64 entries × 2 Newton iterations is
     the knee (2 ULP). 256 entries buys nothing, a third iteration buys
     nothing, 16 entries would need a third iteration — 12 more pipeline
     stages. The model's own exponent normalisation was wrong first and
     produced a constant ~5.6% error, caught by its self-test before any
     Verilog existed; had it survived, every testbench would have passed
     against a wrong reference.

[E2] Answer the obvious attack on a binary32 accelerator: nbody's correctness
     measure is energy conservation, which is exactly what precision loss
     degrades.
RESULT: 2ff5784, precision_study.py. Over 2000 steps the binary64 reference
     itself drifts 2.104e-05 — the integrator's own truncation error. The
     accelerator's contribution with binary64 state is 1.818e-08, about a
     thousand times smaller. With binary32 state as well it is 1.346e-05, 740x
     worse. So the loss is in accumulation, not in the kernel: narrow multiply,
     wide accumulate.

[E3] Build fp32_mul and fp32_add, and verify against the model.
     PROMPT AS SENT:
       "so in 3 we talk about how we do all the + - * ^ in flooting point"
RESULT: a8ceec0. Two rounding bugs, and how they were found matters more than
     the fixes. The lost sticky bit failed 4 of 512 vectors in tb_pe_pair and
     0 of 512 in tb_dot3 — because pe_pair computes dot3(d,d), a vector
     against itself, which always carries out, and tb_dot3's independent
     random vectors structurally could not produce that. The rounding carry
     failed 1 of 512. With 100 vectors we would have shipped it.

[E4] Build dot3 and rsqrt as shared units both PEs instantiate.
RESULT: 376f4fb. The rsqrt seed table failed 486 of 512 vectors. The fix
     changed the representation, not the logic — the index became a bit
     concatenation of {exponent parity, top mantissa bits}. A failure rate
     that high is an encoding problem, not an arithmetic one.

[E5] tb_rsqrt reports 0 ULP, which is better than the model's swept maximum of
     2 ULP. Do not report 0. Work out why the test is too kind.
RESULT: 376f4fb. The 512 vectors do not include the model's worst case near
     x = 1.018e-06. The module header documents the honest 2 ULP bound from
     the sweep. Same lesson as [E3] from the other side: a green test is a
     statement about your stimulus.

[E6] The Sun comes out wrong by the largest margin, Jupiter less, Neptune
     least. Diagnose it.
     PROMPT AS SENT:
       "what is the 49 thing ? and why 49"
       "ok to understand all this , i need to understand what is a pair ....
        and eveything about this two benchmarks"
RESULT: 19d4728, 821ad45. A read-after-write hazard that exists only because
     the pipeline is 49 deep: body 0 appears in four pairs issued on
     consecutive cycles, so pair (0,2) read its velocity 48 cycles before pair
     (0,1) wrote it. Error magnitude correlating with how often a value is
     touched means a dependency, not arithmetic. Fixed by dropping Newton's
     third law (twice the pairs, half the hazard) plus 4 round-robin partial
     accumulators — 4 because it must exceed the adder's 3-cycle latency.

[E7] Measure what a Python→C crossing actually costs before designing the
     interface.
RESULT: 188a9c5, 821ad45. ctypes with 3 doubles: 595 ns, against pe_pair's
     68 ns latency and 2 ns throughput interval. At nbody's 10 pairs per
     timestep the crossing is still 87% of the call, so batching pairs is not
     enough — hence N_STEPS in the descriptor, and a hand-written C extension
     rather than ctypes. The measurement made both decisions.

[E8] Bound the speedup with Amdahl's law from our own measured f, and state
     the method.
     PROMPT AS SENT:
       "so is this hw making it faster ?"
       "ok in the start the hw is an accelator , but can it be used as an
        accelator in some case"
RESULT: 188a9c5. nbody f = 0.657 → 2.66x total; raytrace f = 0.512 → 2.04x.
     raytrace's kernel is 12x faster (244x vs 20x) and its total is lower,
     because f is lower. Two versions are committed, method A and method B,
     because f was measured on the baseline profile and applying it to the
     optimized runtime mixes two things; the report quotes B and states the
     limitation.

[E9] psel is delayed 49 cycles and every result lands in the wrong partial.
RESULT: 821ad45. Total issue-to-result latency is 52, not 49 — the
     delta-subtract stage sits in front of the PE. Silently wrong, no error
     flag. The source now notes the better pattern: derive alignment from a
     signal already delayed correctly, rather than re-deriving the number by
     hand.

[E10] Draw the block diagram.
     PROMPT AS SENT:
       "explain the block diagram , it supposed to explain all ?"
RESULT: ba9b99a. Redrawn once. The first version drew every signal as an edge
     and produced a technically complete mesh that told the reader nothing.
     The architectural claim is that dot3 and rsqrt are one design instantiated
     by both PEs, so the second version draws containment and marks the DMA
     edges "ONCE per run" — the batching argument drawn rather than argued.
